# 运营现状：把做过的事与得到的结果分开

任务是核对已有结果，不预支未来成绩。原书以发展历程、成果展示、财务现状组织材料，用“九有”观察项目发展。九项并非固定晋级顺序，也不需要每个项目都拿融资才算成熟。

## 先确定可比较的范围

优先读取已有材料，提取项目、统计截止日、业务范围、数据周期和用户想做的判断。日流水不能直接对比整月收入，不同版本的同名指标也不能直接连成增长曲线。

资料不足时，先整理能确定的结果。只追问会改变结论的口径，例如“这十万元是签约金额、确认收入还是实际收款”；不要求早期项目补齐三年财务报表才继续。

## 核对流程

### 1. 建立时间轴和结果轴

时间轴只留改变项目状态的事件：产品可用、首笔交易、交付完成、团队加入、重要合作或融资到账。结果轴保留这些事件证明了什么。举办活动、获得奖项、完成页面与真实使用、成交、有效交付分别记录。

每个重要结论带上：发生时间、统计范围、证据出处及局限。区分用户陈述、材料记录、外部核验、分析推断和待验证假设。合同能支持某项约定存在，不自动支持全部交付、收入确认或款项到账。

### 2. 用“九有”检查，而非打总分

| 节点 | 检查重点 |
| --- | --- |
| 有创意 | 问题、对象和解决构思是否具体 |
| 有团队 | 是否有实际投入与明确承接，而非只列成员 |
| 有产品 | 原型、可用版本、可交付版本分别到了哪一步 |
| 有公司 | 主体的实际状态；不把注册当作需求成立 |
| 有销售收入 | 交易是否真实、口径是什么；意向与订单单列 |
| 有利润 | 收入和成本是否同周期，毛利、净利是否混用 |
| 有规模 | 数量相对什么基线增长，交付与成本怎样变化 |
| 有可持续性 | 结果是否跨周期重复，是否依赖一次事件或单一客户 |
| 有融资 | 约定、交割与到账分开；融资不替代客户验证 |

每项按实际证据写“已有支持 / 部分支持 / 暂无支持 / 当前不适用”，附一句理由。状态标签为应用扩展，不是原书评级。未看到材料只能说明尚未核实，不能直接写“没有”。

### 3. 拆开经营与财务口径

订单额、确认收入、现金到账、毛利和净利分别列示；订金、退款、未交付责任和税费等按影响程度说明。没有成本明细就不能由销售额推出盈利。经营测算不冒充审计或正式会计结论。

用户数说明注册、活跃、付费的定义；复购应看有机会再次购买的群体及观察期，不能以尚未进入复购窗口的人直接计算“失败率”。不适用复购的产品，可看持续履约、推荐或其他与业务相符的后续行为。

有数据矛盾时，保留两个数及各自日期、来源、口径，先解释可能差异，再确定所需核对材料；不要取较大值、均值或最新口述强行消除冲突。

### 4. 找到最关键的证据断点

按用户目标判断结果意味着什么：有原型但无人使用，主要缺使用效果；有用户但没付款，付费假设仍未知；有收入但持续亏损，先核对成本和获客；有利润却回款慢，关注现金时序。

上述是条件判断，不是所有行业都按同一顺序发展。稳定的小生意可凭目标范围内的持续盈利证明价值；早期长研发项目可报告技术或交付里程碑，同时明确尚未验证市场和盈利。

## 交付与完成条件

先给一句阶段判断，再提供必要的证据表：结论 / 证据 / 口径和时间 / 尚不能证明什么。需要完整报告时补时间轴、“九有”状态及财务口径对照。

结尾只给当前最有价值的一项补证动作，说明补什么材料或观察什么结果，以及它会改变哪个判断。新实验的详细设计不在这里重复展开。

当“已证明、未证明、存在冲突”已经分清，且关键缺口有下一步时即完成。新增交付记录、财务校正或跨周期结果出现后再更新；不得回改旧结论使其看似当时已知。
