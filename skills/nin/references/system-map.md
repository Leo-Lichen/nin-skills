# 系统地图与路由案例

需要全套介绍、辨别复杂路由或核对原书覆盖时阅读。日常具体问题不必全读。

## 原书的骨架

“12379”（PDF 12—20）：一个核心是完整的问题解决方案；两个功能是对外融通资源、对内作为行动地图；三个价值是问题、方案、团队；七问是 What、Why、How、Who、When、Where、How much；九模块由“936”展开。

“936”（PDF 19、23—52）是九模块三十六要点：

| 模块 | 原书要点 | 专项 |
| --- | --- | --- |
| 公司简介 | 封面要素、业务描述、理念表达、优势亮点 | positioning；bp |
| 市场机会 | 背景趋势、需求痛点、竞品不足、市场规模 | market |
| 产品介绍 | 产品概况、技术创新、比较优势、门槛壁垒、应用场景、效果验证 | product |
| 商业模式 | 运营模式、盈利模式、营销模式 | model |
| 团队组织 | 核心团队、股权结构、公司架构、专家顾问 | team |
| 运营现状 | 发展历程、成果展示、财务现状 | progress |
| 战略规划 | 战略目标、实现路径、资源投入（成本） | strategy |
| 风险管控 | 宏观风险、产品风险、运营风险、团队风险 | risk |
| 融资计划 | 融资方式、项目估值、资金用途、退出方案、对赌条款 | funding |

模型是思考覆盖，不是必须出现的幻灯片目录。例如不需要融资的内部经营计划，可以说明资金安排，不必编造估值与退出路径；对赌列为识别事项不代表鼓励采用。

后半部对应：BP 五特征（54—59）→ bp；路演四方面（62—67）→ pitch；六脉神剑与七伤拳（70—77）→ investor；独孤九剑（80—85）→ experiment、strategy、survival、founder；十大关系与五力（84—91）→ founder；三板斧（99—101）→ survival。

project 的状态结构与文件工具属于工程扩展。它保存证据和判断的变化，不新增商业理论。

## 场景一：从需求直接进专项

用户：“培训机构负责人很喜欢我的 AI 批改工具，老师说费时间，帮我重新设计试点。”

正确路由：experiment。保留负责人可能付费、老师实际使用的差异，把“愿意买”与“真实工作量减少”拆成不同假设；需要产品使用步骤时局部参考 product。已经明确要试点，不先问要诊断还是体检，也不强行把九模块全部走完。

错误路由：“你缺流量，先做品牌定位，再做市场，再写 BP。”它无视用户指定交付，并把待验证原因当成结论。

## 场景二：短期现金与长期目标冲突

用户：“只有两个月现金，但现在想扩招销售冲规模。”

先看用户任务：若问“该不该扩招”，survival 先核对现金时间与已验证销售效率；若明确要“列出扩招方案的预算”，仍交付预算情景，把回款延迟和支出时点写入，而不是只劝融资或拒绝规划。

完成后可建议 model 核对获客与交付是否能重复，但不能自动启动所有专项。

## 统一证据语言

“用户陈述”是用户提供但尚未独立核对的信息；“材料记录”指可定位文件中的记录；“外部核验”标明来源与日期；“推断”写清依据和不确定性；“待验证”说明如何检验。记录来自哪里，不因它被写入报告就升级可信度。

交接示例：“目标是三个月内形成稳定兼职收入；用户称上月有五单，尚无成本表；已确认不做融资；本次需要确认交付能否重复。请保留这个经营目标，先核对单次工时和可承受获客投入。”
